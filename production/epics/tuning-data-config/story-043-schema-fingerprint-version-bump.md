## Implementation Notes

*Derived from ADR-0004 section 2 and the Amendments (REVISED spec for story 043):*

- Why the history exists: a generated fingerprint beside a hand version cannot detect change on its own. The committed pairing is the append-only `TuningSchemaHistory[]` (one `{Version, Fingerprint}` entry per bumped version), and the test compares the freshly generated fingerprint with the entry of the current `TuningSchemaVersion`.
- Placement: `Source/StealthFoundation/Public/Server/StealthTuningVersion.h` (guard header first) holds `TuningSchemaVersion` (the constant Session's join gate reads through `UStealthTuningStore::GetSchemaVersion`, later story) and `TuningSchemaHistory[]`. The generated fingerprint constant is written into `Source/StealthFoundation/Private/Tuning/StealthTuningSchema.generated.inl` by the story 041 generator (extend it through the extension point left there). The test is `Source/StealthGameEditor/Private/Tests/Tuning/SchemaVersionBumpedTest.cpp`.
- Fingerprint covers names, types, audiences, latches and enum values, not defaults or ranges. A change to a default value only is outside the fingerprint list; the spec says to confirm that is intended. Treat it as an open design confirmation for the story reviewer, not a decision made here.
- Hash algorithm for the fingerprint is not fixed by the inputs (open). It must be stable across platforms and engine versions, so not `GetTypeHash` and not `UE::HashStringFNV1a` (a string API that widens characters [V `Hash/Fnv.h`]). The project's own FNV-1a-64 byte function is story 045, a sibling of this story (both depend on 041, neither on the other), so 043 cannot rely on it; either write the small byte hash so that story 045 can reuse it, or use a separate simple stable hash and record it.
- Initial `TuningSchemaVersion` value and the first history entry are not specified by the inputs (open); create the first entry from the generator output at the time this story lands.
- Test cases: (a) generated fingerprint equals the current version's history entry: pass; (b) a seeded field change with the version untouched: fail; (c) after the bump plus history append: pass; (d) two history entries with the same fingerprint: fail. Cases (b) and (d) are the negative controls; (b) must be watched to fail once (ADR-0008 section 3), recorded in the story close note. Implement the seeded change as a fixture or a parameterised comparison, not by editing real tuning structs in the test.
- Known limit (spec edge): removing an old history entry is not detected by this test; if that is required it needs a G3-style shrink-only check, which is not in this story.
- Test class `FTuningSchemaVersionBumpedTest`, name `StealthGame.Tuning.SchemaVersionBumped`, flags `EAutomationTestFlags::EditorContext | EAutomationTestFlags::ProductFilter`, whole file in `#if WITH_DEV_AUTOMATION_TESTS`; runs with the editor automation suite (`^StealthGame.`).
- Prototype: none (no `Prototype:` line in the plan).

## QA Test Cases

*Written by qa-lead at story creation. The developer implements against these, do not invent new test cases during implementation.*

- **AC-1**: The test fails on a field change without a bump and on duplicate fingerprints across versions.
  - Given: the generated fingerprint and `StealthTuningVersion.h` with `TuningSchemaVersion` and append-only `TuningSchemaHistory[] = {Version, Fingerprint}`.
  - When: the generated fingerprint is compared with the history entry of the current version; a seeded field change is run once; two history entries share a fingerprint.
  - Then: matching passes; a field change without a bump plus history append fails (watched to fail once); duplicate fingerprints across versions fail.
  - Edge cases: removal of an old history entry is not detected by this test (needs a G3-style check if required).
